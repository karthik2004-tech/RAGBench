# RAGBench — RAG Evaluation & Optimization Framework

## Complete Project Context / Handoff for New Chat

I am building an AI/ML portfolio project called **RAGBench — RAG Evaluation & Optimization Framework**.

The goal is to build a Retrieval-Augmented Generation (RAG) system and, more importantly, evaluate how accurately, reliably, and efficiently the RAG system works.

I want this to become a strong **AI/ML Engineer / Data Scientist portfolio project** that demonstrates understanding of:

* RAG
* Transformers
* Sentence Transformers
* Embeddings
* Vector databases / vector search
* FAISS
* Information Retrieval
* Cosine similarity
* LLMs
* Hallucination detection
* NLI
* Evaluation metrics
* Experimentation
* System optimization
* Latency measurement
* Failure analysis

I do NOT have a GPU or significant local computational resources, so the project should remain **CPU-friendly and local-first** wherever possible. Free Google Colab can be used for heavier experiments if necessary.

---

# 1. Core Project Idea

A traditional RAG project asks:

> "Can I build a chatbot that answers questions from documents?"

RAGBench asks:

> "How accurate, reliable, and effective is my RAG system?"

The project should therefore measure both:

### Retrieval quality

* Recall@K
* Precision@K
* MRR / Mean Reciprocal Rank
* Hit Rate

### Generation quality

* Faithfulness
* Answer Relevancy
* Eventually answer correctness
* Potentially context relevance / groundedness

### System performance

* Retrieval latency
* Generation latency
* Total latency
* Experiment comparison

The major portfolio value is that the project does not merely call an LLM API. It measures and analyzes the behavior of the RAG pipeline.

# 5. V1 Indexing

File:

```text
src/rag/index.py
```

The current implementation:

1. Reads `.md` and `.txt` files.
2. Splits text into fixed-size character chunks.
3. Uses:

```text
chunk_size = 400
overlap = 50
```

4. Creates records containing:

```text
chunk_id
doc_id
text
```

5. Generates embeddings using:

```text
all-MiniLM-L6-v2
```

6. Converts embeddings to float32.
7. Normalizes them with:

```python
faiss.normalize_L2(embeddings)
```

8. Uses:

```python
faiss.IndexFlatIP(dim)
```

Because embeddings are normalized, inner product approximates cosine similarity.

9. Saves:

```text
data/index/index.faiss
data/index/records.pkl
```

Important V1 limitation:

The chunking is based on **characters**, not tokens or semantic/sentence boundaries.

This is something to improve in V2.

# 6. V1 Retrieval

File:

```text
src/rag/retrieve.py
```

The retriever:

1. Loads the FAISS index.
2. Loads the chunk records.
3. Loads the same MiniLM embedding model.
4. Embeds the user's question.
5. Normalizes the query embedding.
6. Searches FAISS.
7. Returns top-K chunks.

Default top-K:

```text
k = 3
```

Each retrieved result contains approximately:

```text
chunk_id
doc_id
text
similarity score
```

# 8. V1 Retrieval Metrics

File:

```text
src/eval/retrieval_metrics.py
```

Current V1 metrics:

### Recall@K

Checks whether the expected ground-truth chunk appears in the top K retrieved chunks.

### Precision@K

Current implementation assumes only ONE ground-truth chunk per question.

Therefore, if one correct chunk is found in top 3:

```text
Precision@3 = 1/3
```

If none is found:

```text
Precision@3 = 0
```

### Reciprocal Rank

If the correct chunk is ranked:

```text
1 → reciprocal rank = 1
2 → reciprocal rank = 0.5
3 → reciprocal rank = 0.333
```

If not found:

```text
0
```

### MRR

Mean Reciprocal Rank across evaluation questions.

Important V2 improvement:

The metric system should eventually support **multiple relevant chunks per question**, because real RAG questions can be answered using several chunks.

# 9. V1 Faithfulness

File:

```text
src/eval/faithfulness.py
```

Faithfulness is evaluated using an NLI model:

```text
cross-encoder/nli-deberta-v3-small
```

The system:

1. Splits the generated answer into claims/sentences.
2. Treats retrieved context as the premise.
3. Treats each generated claim as the hypothesis.
4. Uses NLI to determine whether the context entails the claim.
5. Uses an entailment threshold.

Default threshold:

```text
0.5
```

Faithfulness is calculated as the fraction of claims judged entailed.

Important V1 limitations:

* Naive sentence/claim splitting.
* NLI is being used as a heuristic.
* Context aggregation can affect NLI.
* It is not a complete factual correctness evaluator.

These can be improved later.

# 10. V1 Answer Relevancy

File:

```text
src/eval/answer_relevancy.py
```

The system embeds:

```text
question
answer
```

using MiniLM and calculates cosine similarity.

Higher similarity means the answer is more semantically related to the question.

Important limitation:

Semantic similarity does NOT necessarily mean the answer is factually correct.

Example:

An answer can be highly similar to a question but still contain incorrect information.

This is another V2 improvement area.

# 18. Current Interpretation of the Evaluation

The generated answer is essentially identical to the ground-truth answer:

```text
Radar
LiDAR
Ultrasonic sensors
Cameras
```

But the retrieved chunks were:

```text
sample_doc_chunk_3
sample_doc_chunk_4
sample_doc_chunk_2
```

while the expected chunk was:

```text
automobile_doc_chunk_0
```

Therefore:

```text
Recall@3 = 0
MRR = 0
Precision@3 = 0
```

These metrics are behaving according to the current implementation because the expected chunk was not retrieved.

The generated answer has:

```text
Answer Relevancy = 0.838
```

This means the answer is semantically related to the question.

However:

```text
Faithfulness = 0
NLI entailment score = 0.003
```

This likely means the retrieved context did not contain enough information to support the generated answer.

This creates an important RAG failure case:

```text
Question
   ↓
Poor retrieval
   ↓
Wrong/irrelevant context
   ↓
LLM still generates a correct-looking answer
   ↓
Faithfulness detects that context does not support it
```

This is actually useful for demonstrating why RAG evaluation is necessary.

# 20. Important V1 Limitations

V1 is intentionally a baseline/prototype.

Current limitations:

### Dataset

Only a very small evaluation dataset.

Need eventually:

```text
100–300+ questions
```

with carefully curated ground-truth answers/chunks.

### Retrieval ground truth

Currently assumes:

```text
one question → one ground-truth chunk
```

Real-world RAG can have:

```text
one question → multiple relevant chunks
```

### Chunking

Current:

```text
fixed character chunks
```

Need better:

```text
sentence/paragraph/token-aware chunking
```

### Retrieval

Current:

```text
FAISS top-k
```

Need potentially:

```text
FAISS top-20
      ↓
Reranker
      ↓
Top-5
```

### Answer relevancy

Currently uses embedding similarity.

This is useful but incomplete.

### Faithfulness

Current NLI approach is a heuristic and should be improved.

### Experimentation

V1 doesn't yet have a robust experiment runner.
